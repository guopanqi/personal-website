# Gamer520 每日更新 Skill

Gamer520 是发现来源，不是游戏库的唯一来源。游戏库一行只代表一款游戏；评分、理由与备注属于用户自己的判断。manual 条目被 Gamer520 扫到时只确认“已收录”，绝不新建、合并或覆盖。

CLI 参考见 游戏收集agent/game_library_cli/README.md。

## 运行环境

所有命令使用项目脚本：

~~~bash
游戏收集agent/game_library_cli/game-library <子命令>
~~~

不要使用 uv run --project ... game-library ...。项目脚本复用已安装的 .venv，避免受限环境重新下载依赖。

## 数据边界

- 判断库：游戏收集agent/game-library.csv
- 来源同步状态：游戏收集agent/gamer520-sync-state.json
- 口味基准：游戏收集agent/taste.txt
- 相似标题复核：游戏收集agent/game-library-doctor-reviews.json

字段语义：

- 标题：名称规范化时，若能核实游戏的中文名和英文名，优先写作“中文名 English Name”，便于双语搜索与识别；只记录有来源依据的名称，不自行翻译或猜测英文名。只有一种名称可核实时，保留该名称即可。
- 收录日期：游戏进入判断库的日期。
- 收录来源：只可能是 gamer520 或 manual，代表首次收录来源，创建后不可变。
- Gamer520帖子日期：仅 Gamer520 条目有值；不是游戏发行日期，也不是全库排序依据。
- 来源链接：Gamer520 条目必填；manual 条目可为空。
- 状态继续放在 用户备注，例如 wishlist；需要 PC。

游标绝不能从游戏库推导。手工收录条目不可影响 Gamer520 的扫描边界。

## 总流程与职责边界

这个 Skill 只负责把“来源发现”编排成“个人游戏判断”。主流程只有五步，用户反馈是事后的回写环：

1. Provider 获取信息：来源接入层从 Gamer520 等发现来源取得候选和来源游标。当前自动实现是 Gamer520 Provider；其他来源可以作为核验来源或手工候选来源。
2. CLI 去重与分类：CLI 根据标题、链接、平台和复核账本，把候选分为 existing、platform merge、ambiguous 或 new。CLI 只做确定性匹配，不判断游戏好不好玩。
3. Agent 判断：对 new 候选先依据 Gamer520 详情做初评；对达到外部核验条件的候选调查 Gamer520 之外的资料，再独立复评实际玩法与口味评分，最终结论才可写入。
4. CLI 写入与验证：CLI 以 dry-run 预览，再正式写入、排序、校验和检查重复。Agent 不直接编辑 CSV。
5. 来源状态推进：全部候选已写入或明确跳过、数据库验证通过后，CLI 才推进对应来源的同步状态。

反馈回写：用户补充 `wishlist`、玩过、兼容性或实际感受时，CLI 更新用户备注；Agent 比较反馈与原判断，只有明显偏离时才提出修改 `taste.txt` 的建议。

职责边界：

- Provider/来源接入层：负责某个来源自己的抓取、解析、详情页读取、日期/链接规则和游标语义，并返回统一格式的候选。当前只有 Gamer520 Provider。
- 游戏库 CLI：去重、写入、更新、排序、validate、doctor，以及安全推进来源状态。
- Agent/本 Skill：编排流程、做同一性语义裁决、详情页初评、外部资料核验与复评、口味评分和反馈复盘。
- `game-library.csv`：保存最终的个人判断，不保存来源扫描进度。
- `gamer520-sync-state.json`：保存 Gamer520 已扫描到哪里，是来源同步检查点，不是游戏库内容，也不是 Agent 记忆。
- `taste.txt`：保存用户口味基准，未经用户同意不修改。

因此，来源游标不是 Gamer520 传回来的“游戏信息”，而是 Provider 维护的来源同步状态：它只回答“下次从来源的哪里继续扫”。它属于 Gamer520 Provider，不属于游戏判断本身。Provider 的概念边界现在明确，但不要求立刻把代码重构成多来源插件框架。

通用约束：通过 CLI 读取局部库状态，不直接编辑 CSV，也不直接读取整份 CSV；非独立游戏（公告、下载说明、补丁、工具、资源合集、站务文章）不得入库；扫描不完整、dry-run 失败或写入后校验失败时，禁止推进来源游标；用户反馈可以更新用户备注，修改 `taste.txt` 必须先取得用户明确同意。

## 1. 预检与扫描

先运行：

~~~bash
游戏收集agent/game_library_cli/game-library validate
游戏收集agent/game_library_cli/game-library doctor --json
游戏收集agent/game_library_cli/game-library source gamer520 scan --platform all
~~~

`source gamer520 scan` 的游标来自 gamer520-sync-state.json，输出中每个平台包含 next_cursor。结果必须 complete: true；否则提高 --max-pages 重跑。

候选处理：

| 输出 | 处理 |
|---|---|
| existing | 已有同一游戏，跳过。若 match.source=manual，尤其不得改写它。 |
| platform_merges | 仅对已有 Gamer520 条目，确认后可将平台更新为 PC/Switch。 |
| new | 抓详情、评估并新增为 gamer520 条目。 |
| ambiguous | 对高相似标题做同一性判断；未确认前不写入。已记录 distinct 的候选按 new 处理，已记录 same 且无冲突的候选按 existing/platform_merges 处理。 |
| cross_platform_candidates | 确认同一游戏后只写一条 PC/Switch Gamer520 记录。 |
| Doctor unresolved_candidates | 用 doctor-review 记录同一/不同结论。 |

精确标题的 manual 匹配直接属于 existing，因为库的重复规则优先于来源扫描。中文/英文名、重制版等高相似匹配必须人工确认。

## 2. 游戏判断、语义裁决与评分

Gamer520 只是发现来源，不是游戏玩法与质量判断的可信依据。Steam 商店页、官网和发行商介绍同样属于营销材料，只能用于确认事实、功能和开发者声称的卖点，不能直接作为最终评价。

### 2.1 游戏同一性裁决

每个 new 候选先抓详情：

~~~bash
游戏收集agent/game_library_cli/game-library source gamer520 scrape-detail <URL>
~~~

判断阶梯：

1. 比较规范标题、英文名、系列编号、平台、描述与链接。
2. 仍不确定时抓 Gamer520 详情。
3. 仍不确定时查 Steam、官网或发行商一手来源。
4. 确认不同：`doctor-review --decision distinct`，随后按 new 处理；确认同一：`doctor-review --decision same`，随后按 existing/platform merge 处理。扫描器会读取复核账本，已确认的 distinct 不再重复判为 ambiguous。
5. 仍无法判断才交给用户。

### 2.2 详情页初步判断实际体验

先只根据 Gamer520 详情形成玩法与体验的初步假设，明确区分来源原文和自己的推断，不把商店宣传语直接当结论。此阶段的判断和评分均为“初评”，不能冒充最终结论。按以下三层整理初步认识：

1. **操作与决策循环**：玩家反复执行什么、反复解决什么问题、凭什么信息作选择、承受什么后果；成长、养成或 meta progression 怎样参与这些活动与后果；它最接近什么成熟模板。
2. **体验驱动力**：玩家为什么愿意继续。可能是发现、人物关系、策略后果、氛围、音乐与身体参与、共同表演、挑战掌握或数值增长。它不一定等于耗时最多的动作。
3. **成立情境**：价值主要在单人长期游玩、短期体验、多人合作、聚会，还是设计研究中成立。

操作循环负责揭穿换皮，体验驱动力负责避免把侦探游戏概括成“走路和读文本”、把聚会游戏概括成“按键和刷分”。例如，房间战斗、随机强化、Boss 和永久成长构成的主体应判断为动作肉鸽；海域和伙伴只有显著改变决策时才算结构差异。节奏或舞蹈游戏如果主要通过音乐、身体表达和共同参与成立，则不能仅因操作占比高而机械判为纯反应雷区。技巧游戏中的路线发现、空间阅读和环境穿行也可能是独立驱动力，不能未经核验就降格为风景包装。


在按口味判断某项机制是吸引力还是限制前，先说明它在整体体验中的作用。战斗、养成、经营或重复动作可以承担人物处境、关系、叙事节奏、探索或身体表达。用可核验的“具体活动或规则 → 玩家经历的处境、感受或后果”说明这种作用；不要先把它们拆成玩法成本，再用剧情补偿。机制参与讲故事不要求战斗结构创新，也不要求系统与剧情双向改变；预设事件、能力差距或行动限制同样可能形成叙事体验。无法确认时补查并保留未知，不编造整合关系。

将机制列为“摩擦”时，必须指出哪项实际要求触及哪条口味限制，例如重复刷资源、反复重试或为推进内容被迫优化数值；不能仅凭“武侠”“回合制”“养成”或耗时占比认定。机制的叙事作用与实际负担可以同时成立，应分别说明证据；有故事不免除对重复、操作负担的判断，也不覆盖 Taste 的无条件排除项。

### 2.3 初评后的外部资料核验与复评

每个 new 候选先依据 Gamer520 详情完成初评并给出暂定分数，再决定是否需要外部核验。初评只用于筛选研究优先级，不是最终评分。采用两阶段漏斗，不对所有候选做深度搜索：

- 初筛明确命中 `taste.txt` 无条件排除项、且无身份或玩法疑点的候选，可直接按 1–2 分处理，不扩展研究。一般不喜欢的类型不能仅凭类型标签认定没有研究价值。
- 初评暂定达到 3 分、看起来可能有特殊设计（尤其可能改变玩家实际活动和决策的规则）、或无法确认主循环的候选，必须进行低成本联网核验。来源简介很短、标题不规范或详情缺失时，\"无法确认\"本身就是触发条件，不能直接以信息不足结束。

联网核验的目标是确认“实际怎么玩”，优先级如下：

1. 实机视频、长篇 gameplay、Let's Play；
2. 玩家评测与讨论；
3. 独立媒体评测；
4. Steam 用户评论；
5. 开发者日志、Steam 商店、官网；
6. Gamer520 详情。

搜索要确认：一局、一天或一个章节的实际流程；游戏时间主要花在哪里；重复结构和刷数值程度；叙事、探索、经营、伙伴等系统占比及它们与战斗、成长等活动的具体联系；所谓创新是否真的改变玩法决策；以及它是否只是已有模板的变体或换皮。

不需要为了查全而查全。2–3 个独立来源已经稳定确认核心循环时就停止搜索。外部证据冲突时标记“判断置信度低”，不要强行下结论。完成核验后，必须重新判断实际主循环、体验驱动力、成立情境、结构差异、个人/研究/形式/情境价值及主要限制，并重新决定最终评分；不能只把外部资料附加到初评理由后而保留未经复判的分数。最终评分可上调、下调或维持，理由要说明外部证据如何支持或改变初评。

“信息不足”是补查后的结论，不是来源文本不足的同义词：先以规范标题、英文名、开发商或平台线索检索 Steam、官网、实机视频、商店评论或独立报道；只有仍无法确认同一游戏或实际主循环时，才标记信息不足。若能确认游戏本体但证据有限，应给保守评分并标注低置信度，而不是把它归入信息不足。

### 2.4 识别玩法的内在形态与实质性创新

Agent 对每款候选按四层理解：

1. 操作与决策循环：玩家反复执行哪些活动、处理哪些信息、作何选择、获得什么反馈与后果。
2. 结构变化：是否真正改变既有类型的决策空间、信息、资源、时间、空间、风险、失败或成长方式；是否因此形成不同的体验。
3. 内容与主题变化：新世界观、故事、角色、任务、职业或对象，但玩法结构基本不变。
4. 表现层：美术、音乐、视觉风格、动画和氛围。

第 3、4 层仍可具有独立的审美、叙事或形式价值，但不能直接算作玩法结构创新。分析时要识别最接近的成熟玩法模板，并用三个问题检验所谓的新意：

- **剥去题材后还有什么不同？** 把龙替换回作物、把经营对象或美术换回常见版本，玩家原本的日常安排、取舍和反馈是否基本不变？如果是，主要是题材或内容变化。
- **有没有新的活动或新的决策问题？** 新规则是否要求玩家作出过去不需要的观察、推理、操作、权衡或表达？例如裁缝题材只有实际引入剪裁、拼合、设计约束等新的互动问题，才构成玩法层面的新意；不能仅凭职业设定或截图断言。
- **如果还是熟悉的类型，是否实质推进了它？** 一项改动虽未创造全新类型，但若持续改变位置判断、时间压力、资源关系、行动后果或策略可能性，也可以是值得关注的创新。不能因为仍叫“回合制”就忽略差异，也不能因删去格子或叠加机制便自动认定创新。

结论只需区分：**新活动 / 类型的实质变奏 / 主要是包装或内容变化 / 证据不足**。不设置机械的创新分数。可以用一句可核验的话陈述：“相对于【已有模板】，它用【具体规则】改变了【玩家的活动或决策】，因此带来【新的体验或策略可能】。”说不清变化时，不写“玩法创新”。

**新颖性与完成度分开看**：勇敢但不成熟的实验可以有明确的设计研究价值；熟悉但执行出色的游戏同样可以推荐。以可观察的规则与实际玩法为依据，勿把宣传声称的“创新”当成已证实的事实。

### 2.5 价值与推荐判定

推荐不是“是否符合最常见的单人口味”的同义词。分别检查：

- 个人体验：用户在实际成立的情境中是否可能喜欢；
- 研究价值：是否创造新活动、推进成熟类型的决策结构，或通过机制组合、叙事连接、涌现故事、优秀类型执行提供值得研究的设计；探索尚不成熟并不自动失去研究价值；
- 形式价值：美术、声音、交互形式或氛围是否提供启发；
- 情境价值：多人、聚会、身体参与或共同表演是否构成主要体验。

“明确雷区”是限制，不是自动否决。只有当上述正向价值都不足，主要体验又落入明确雷区时，才判为不推荐。不要为了推荐而虚构创新点；没有结构创新时可以直说主要价值在表现、情境或优秀执行。

正向价值不必占据最多时间或压过主循环：只要它在实际游玩中持续影响玩家的选择、感受或使用情境，就可以支持“推荐但有雷区”。只停留在题材、宣传或偶发片段中的卖点不算；`taste.txt` 明确写为无条件否决的硬雷区仍优先。

研究价值必须足够鲜明：它应提供值得单独分析的新活动、实质性结构变奏、机制组合、表达方法或特别优秀的执行。探索未必成功，但应能指出具体在尝试什么以及它怎样改变玩家的问题；红线类型里一个常见的小变化、题材变化或局部战术差异，不足以单独触发推荐。

推荐强度：

- **必须推荐**：能够明确说明用户为什么会优先实际体验，而不只是觉得它值得研究；同时作品还有明显创新、完成度、启发性或单项突出表现。若主要依据只是类型关键词，或明显摩擦很可能阻止用户持续体验，则降为“推荐”。
- **推荐**：个人体验、研究、形式或情境价值中至少一项明确成立，但不一定需要优先体验。
- **不推荐**：缺少足够独立价值，且主要体验落入明确雷区。

仅在研究层面成立，或主要依赖特定多人/聚会情境成立的作品，默认是“推荐”；优秀、重要或经典本身都不能代替明确的个人优先体验意愿。

### 2.6 评分与游戏判断

评分只回答“值不值得用户点开细看”，顺序为：实际体验 → 有效结构差异 → 各类独立价值 → 主要限制。

- 1–2 分：没有足够独立价值，且主要体验命中雷区。
- 3 分：至少一项价值明确成立，但强度一般、仅在特定情境成立或限制明显；有探索线索但尚不足以确认实质差异时，保守处理。
- 4 分：存在经过核验、值得重点研究或体验的强项；实质性玩法探索即使未完全成功、个人游玩兴趣一般，也可能支持此分数。
- 5 分：个人匹配度高，并有非常突出的设计、形式、叙事、探索、经营或氛围价值，应立即打开研究；不能仅因“有创新”就给 5 分。
- 信息不足：完成上述外部补查后仍无法确认同一游戏或实际主循环；宁可单列信息不足，也不要猜测。

每款候选形成一小段“游戏判断”，不设硬性字数：先说明玩家会进入什么处境、受到什么驱动、体验在什么情境成立；再说明操作与决策循环、成熟模板、经核验的有效差异、外围包装和主要限制。**当推荐理由涉及玩法创新时，必须点明“与什么相比、哪条规则改变了玩家的什么活动或选择”；证据不足则明说待验证。**第一层可以有幻想感，但不得复述未经核验的承诺；第二层负责校正第一层。

例如《冰汽时代》可以写成：“你在即将冻死的城市里不断决定谁能活得更好，每次保住秩序都可能牺牲某些人的尊严。设计上它以资源压力、法令和事件选择驱动城市生存，制度选择会转化为人性与政治代价，而不只是建造效率。”

## 3. 统一写入

先对全部 doctor-review、update、remove、add 做 dry-run；全部成功后才正式执行。不得边扫描边写入。

`add` 正式写入必须使用 `--yes`；`--dry-run` 只预览、不写入。

新增 Gamer520 条目的判断、评分和理由必须采用外部核验后的最终复评结论（符合初筛豁免条件的候选采用其有明确依据的初评结论），不得直接写入暂定初评分。新增条目使用当前收录日期和列表页帖子日期：

## 4. 汇报

首行：今天新增 X 款（PC Y / Switch Z）。跨平台更新另列数量。

仅汇报 3 分及以上游戏；低于 3 分但特色鲜明者可补充。按评分降序，同分保持扫描稳定顺序：

游戏名称｜游戏判断｜评分：X/5｜链接

“游戏判断”必须同时包含“玩家体验想象 + 设计层判断”。前半段让人知道这款游戏可能带来什么处境、情绪或驱动力，后半段说明它实际上靠什么循环成立、有什么有效差异和主要限制；不能只是开发者卖点的正面改写，也不能只罗列机制。若主要看点是实质性玩法创新，应直说具体改变了什么；若只是熟悉的循环换了题材，也应坦率说明。

信息不足另起一节：

信息不足，待你判断：

格式：游戏名称｜看不清的是什么｜链接。

新增为 0 时，首行后结束；不写操作日志或客套话。
