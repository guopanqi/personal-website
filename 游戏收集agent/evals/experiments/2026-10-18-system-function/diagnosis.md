# 系统作用与体验负担的诊断

## 问题与证据

本轮由用户反馈触发，开发案例已知，不构成独立泛化验证。原始用户笔记 `src/content/posts/摘录/活侠传-评论.md`：第2—3行明确认为战斗不只是数值、是人物成长的一部分，且不是乐趣核心；第4—5行指出中后期行动集合不再扩展，但人物与选择路线仍构成故事驱动；第7行记录为救人物而学习战斗无用医术的选择；第9行保留后期重复批评。这些是用户体验记录，不作为本轮模型收到的玩法事实输入，也未据此修改获审金标准。

当前 Taste 已包含叙事驱动、体验引擎、具体人物与关系、有意义资源取舍等偏好。它的负向规则限制纯战斗堆数值、重复和让注意力集中于战斗的体验，并没有普遍排除养成。最新反馈与这些正向偏好一致，不能推导用户偏好发生变化。

当前来源 Skill 已说体验驱动力不等于动作耗时，但又把外围包装、成长和 meta progression 并列提问，容易把成长提前判为附属系统。反换皮与创新审查侧重结构差异，执行时可能被错误用于审查叙事价值：未确认战斗创新，就把传统战斗先当限制，再要求剧情补偿。Skill 已允许熟悉结构的叙事与形式价值，故本例也有未遵守现有规则的执行错误。

原 experience-center 候选输出虽将本例评为4，仍直接说传统回合战斗和武侠题材是摩擦；evidence-specificity 及 external-reassessment-v2 输出也仍存在类型式限制。评分变化不能证明这些方法错误已解决。原33例的金标准只有推荐标签和简短原因，本例的简短原因保留后期重复，却没有完整表达系统服务故事。原文中实际体验、结构区别、证据边界等维度的语义审阅不可被推荐率取代。

## 修正规则与过拟合的边界

将“某游戏必须4分”“武侠叙事养成可豁免”或具体剧情答案写入标准，会围绕目标案例拟合；仅使这个案例涨分也不能证明收益。可推广的修正是：机制名称不是体验结论，先解释其在作品中的作用；负面摩擦须落到实际要求和已有口味；叙事作用和重复负担可并存；不要求结构创新或双向分支作为叙事成立条件。

该原则还适用于日程/资源组织故事、成长支持探索、动作参与音乐与社交。它不预设所有这些作品都推荐，也不将叙事作用变为无条件排除项的豁免。因此是针对错误推理方法的可反驳候选，而非已被证明泛化的修复。

## 实验边界

正式 Taste、来源 Skill 和原33个案例保持原状。候选来自当前工作区全文，只改来源 Skill 的机制分析步骤与核验目标，Taste 字节一致。基线与候选由不同的独立 Luna Agent 在无金标准、无对话、无联网的冻结包中判断。33例都是已暴露的开发/回归集，只有标题；未知负向作品可能信息不足，无法充分检验反例与硬排除。结果不证明实际网页核验流程或泛化，不将模型辅助评审填入人工审核记录。
